Inside a Vault-Unlock Failure on the Tiiny Pocket: Diagnosis and In-Place Repair

An encrypted on-device AI vault that refused every login, a missing master key, three factory resets that didn’t help — and the signed SSH repair path that finally brought it back online.

T
Tae Lee
November 7, 2026 · 14 min read · Field Notes
Encrypted vault · LUKS2 detached header · vault-mode key architecture

Resolved

A Tiiny Pocket — a pocket-sized on-device AI computer — booted with its encrypted data vault locked and refused every login. tiiny load, tiiny login, and the TiinyOS desktop app all reported the device as locked, and eventually returned HTTP 500 vault_authkey_seal_failed. This is the full field report: the symptoms, the real root cause, everything that was tried, and the repair that finally worked.

The symptoms

  • tiiny load Tencent/Hunyuan3D-2.1 → Device locked. Use ‘tiiny login’ to unlock the device.
  • GET /v1/data/state → data_state: "locked", requires_unlock: true, key_arch: "vault"
  • From the morning of the incident, POST /api/v1/account/auth (CLI and the TiinyOS app) → HTTP 500 {"error":"vault_authkey_seal_failed"} — the password was accepted, then the seal step failed.
  • The model-serving service (port 8800) and upgrade service (port 5555) were down while the device was locked.

The device’s health endpoint persistently reported:

luks_keyfile : /home/tiiny/keys/userdata.keyfile missing
data_mount   : /data is not mounted but contains files
mapper       : userdata_crypt is not active
target       : data-unlocked.target inactive

The real root cause

The actual fault was a missing credential-wrapped vault master key. The file /home/tiiny/keys/dek.trusted.blob did not exist, even though the material around it did:

FileStateMeaning
dek.trusted.blobMISSINGThe sealed vault master the service needs — the fault
dek.trusted.blob.barepresent (194 B)Bare recovery material
vault.imgpresent (10 MB)Vault image
userdata.luks2.headerpresent (16 MB)LUKS2 detached header
data_crypt_state.jsonpresentkey_arch = vault

The vendor’s own diagnostic kit put it plainly:

“Vault image exists but its primary credential-wrapped blob is missing at /home/tiiny/keys. Bare/other recovery material does not by itself prove a safe recovery path.”

And, crucially:

“A missing legacy plaintext userdata.keyfile is not evidence of damage in vault mode.”

The red herring: the luks_keyfile missing and /data is not mounted health lines are expected in vault mode and were not the fault. The only real problem was the missing dek.trusted.blob. Because that master was gone, the service could not seal an auth key on login → vault_authkey_seal_failed. (That specific error only surfaced after the auth service was upgraded to build 1.0.0-20260923; the older build gave a generic “sign-in failed.”)

What was tried

Self-service — did not fix it

  1. unlock_with_auth_key and tiiny login — authenticated, but the vault stayed locked.
  2. Email-code recovery (tiiny auth forgot-passwd) — HTTP 500 unlock_failed.
  3. Factory reset ×3 via the recovery console, each followed by a fresh tiiny init (Local-only, then Email recovery). Each reset completed cleanly and re-encrypted the vault — but it still would not unlock.
  4. A full cold power-cycle. No change.
Lesson: the factory resets did not help. The real fix rebuilds the master in place from the surviving dek.trusted.blob.bare; a reset re-encrypts the vault and risks destroying exactly that bare material. The resets did not create the fault (the master was already gone before any of them) but they were counterproductive to the real repair.

Vendor repair kits

Support iterated a series of signed kits. Each connects over SSH to the device on a dedicated port using a short-lived support certificate, runs a hash-checked worker plus a helper built from the vendor’s own auth-service source, and operates only on the matching serial and service build.

KitPurposeResult
Diagnostics (r4)Read-only log/state collectionFound the missing dek.trusted.blob
Production upgrade (r14–r16)Install image + upgrade the auth service, then finish via sign-inUpgrade applied; sign-in step stopped. r16 reported vault_authkey_seal_failed
Auth-service collection (r1)Read-only collectionLogs sent to support
Master repair (r1)Reconstruct the master in placeStopped at a strict identity gate
Master repair (r2)Same, relaxed identity checksStopped: PermissionError
Master repair (r3)Same + detailed error reportingExisting master preserved; repair is inapplicable

What actually fixed it

By the r3 run, the master key dek.trusted.blob existed again — most likely re-created by a tiiny init under the upgraded auth service. The r3 message “Existing master preserved; repair is inapplicable” fires only when the master is present and no leftover repair backup exists, and it had already verified the password. A Tiiny support engineer saw this and suggested the obvious next step:

“I see that you already have the dek.trusted.blob. Could you try again with tiiny login?”

A single normal login then succeeded:

tiiny login
Username: sqlreport
Password:
success

Verified unlocked immediately afterward:

GET /v1/data/state
→ { "data_state": "unlocked", "requires_unlock": false, "serivice_status": "ok" }

The four real health errors cleared at once: /data mounted, the userdata_crypt mapper active, data-unlocked.target active, and docker available. The remaining health lines (legacy_*, luks_keyfile, header-backup) are the benign vault-mode items flagged as not-a-fault.

Support then had the device finish with the production update kit, which ran to completion:

Updating Tiiny. Please wait...
Update complete. Saving support files...
Done. You can now use TiinyOS.
Now downloading models

Reference & takeaways

  • The device API requires a Host: auth.api.tiiny header; the authoritative endpoint over USB-C is the gadget link address, with a LAN fallback and discovery at :39218/device.json.
  • The recovery console is armed with POST /api/v1/system/next_boot_recovery (password required), reached after a power-cycle; it exposes /api/recovery/v1/{status,session,operations}. A factory reset re-encrypts the full ~100 GB vault (several minutes).
  • vault_authkey_seal_failed = the auth service cannot seal the auth key because the vault master (dek.trusted.blob) is missing or unusable.
  • Read the health endpoint in context: in vault mode, a missing legacy userdata.keyfile is normal. Don’t chase it.
  • When a vendor’s recovery path rebuilds a key in place, resist the urge to factory reset — you can erase the very material the repair depends on.
